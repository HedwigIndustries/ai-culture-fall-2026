# Продуктовый контекст

**Что:** MR Reviewer — AI-ассистент первичного ревью merge request'ов. Готовит черновик ревью за минуты; публикует и мержит только человек.

**Для кого:**
- основной — автор MR: сам запускает `mr-review` и получает обратную связь до того, как позовёт ревьюера;
- ревьюер (senior / тимлид) — получает MR, где типовое уже исправлено, и при необходимости публикует замечания с подтверждением;
- ИБ — одинаковая проверка обязательных правил на каждом MR.

**Контекст:** бэкенд-команда банка, 10 Python-разработчиков, ~130 MR в месяц (оценка), GitLab. Это обобщённый пример: внутренние данные и код банка в проекте не используются. Это MVP: делаем просто, без лишних сервисов.

**Скоуп MVP:**
- только Python-код;
- правила (безопасность, ошибки, 30 правил кодстайла) + LLM-слой;
- агент только описывает, что исправить; правки кода — в будущем;
- CLI с подтверждением публикации, HTTP API, оценка на открытых данных.

**Как пользуются (MVP):**
- **основной путь — CLI `mr-review`:** сервис агента развёрнут отдельно, разработчик ставит только CLI (`uv tool install mr-review`) и запускает `mr-review <директория репозитория>` (берётся diff ветки от `origin/main`) или передаёт свой diff (`git diff ... | mr-review -`); команда отправляет diff в сервис, печатает черновик ревью и сохраняет его в `.mr-review/` (`latest.md` — последний результат);
- **CLI в репозитории** — для отладки агента и публикации замечаний в GitLab с подтверждением (`--post`).

**В будущем (не в MVP):** вебхук из MR — GitLab сам присылает diff при открытии и обновлении MR, черновик появляется в MR для ревьюера.

**Вне скоупа:** обучение модели, вебхук GitLab и комментарии к строкам, анализ всего репозитория, другие языки.

**Метрики качества:** recall и ложные тревоги на eval-наборе (см. [testing.md](testing.md)).
Экономика считается в отчёте вручную, кода у неё нет.

**Изменения OpenSpec:** `data-collection-analysis` — сбор и анализ данных, `data-preparation` — подготовка данных, `agent-implementation` — агент и его запуск.
