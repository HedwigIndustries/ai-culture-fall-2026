# review-agent Specification

## Purpose
Что делает агент ревью: разбор diff, правила безопасности, ошибок и кодстайла, маскирование, LLM-слой с валидацией ответа, сортировка, лимит мелочей и вердикт без approve.

## Requirements

### Requirement: Разбор diff
Агент SHALL разбирать unified diff на файлы и добавленные строки с номерами строк в новой версии файла. Строки `\ No newline at end of file` не считаются строками файла; удалённые файлы (`+++ /dev/null`) пропускаются.

#### Scenario: Номера строк
- **WHEN** hunk `@@ -1,2 +1,3 @@` добавляет одну строку после первой
- **THEN** добавленная строка имеет номер 2

### Requirement: Правила
Агент SHALL проверять добавленные строки `.py`-файлов 38 правилами: безопасность SEC001–SEC005 (blocker; SEC001 — также в конфигах), ошибки BUG001–BUG003 (major) и кодстайл STY001–STY030 (nit; PEP 8 и типовые проверки). Полный список — в `design.md`. У каждого замечания есть severity, строка и рекомендация текстом; код агент не меняет.

#### Scenario: MR с дефектами
- **WHEN** проверяется `agent/examples/mr_payments.diff`
- **THEN** срабатывают SEC001–SEC004 и BUG001–BUG003

#### Scenario: Кодстайл
- **WHEN** в добавленных строках есть `from os import *` и строка длиннее 120 символов
- **THEN** срабатывают STY008 и STY003 с severity `nit`

#### Scenario: Чистый MR
- **WHEN** проверяется `agent/examples/mr_clean.diff` без LLM
- **THEN** замечаний нет

### Requirement: Вердикт и черновик
Агент SHALL сортировать замечания по severity (blocker > major > minor > nit > question), оставлять не больше 5 nit на MR и выдавать вердикт `request_changes` (есть blocker), `needs_attention` (есть major) или `no_major_issues`. Вердикта approve нет. Черновик SHALL формироваться в markdown и JSON; JSON содержит отброшенные валидацией замечания и пропуски LLM.

#### Scenario: Есть блокер
- **WHEN** среди замечаний есть blocker
- **THEN** вердикт `request_changes`

### Requirement: Провайдеры
Агент SHALL поддерживать провайдеры `openai` (OpenAI-совместимый API, в прототипе OpenRouter), `gigachat` и `none`. Ключи читаются только из `agent/.env`. На каждый `.py`-файл с добавленными строками уходит один запрос с diff файла и списком найденного правилами. При `OPENAI_REASONING=off` рассуждения модели отключаются.

#### Scenario: Без LLM
- **WHEN** провайдер `none`
- **THEN** модель не вызывается, работают только правила

### Requirement: Лимит входа LLM
Агент SHALL отправлять в LLM только файлы, diff которых не длиннее 1 000 токенов (оценка: символы / 3,5). Для файла больше лимита LLM не вызывается: правила по нему работают, а в результат пишется отметка о пропуске.

#### Scenario: Большой файл
- **WHEN** diff файла оценивается в 1 500 токенов
- **THEN** запроса к модели по этому файлу нет, замечания правил есть, в результате отмечен пропуск LLM

### Requirement: Маскирование
Перед отправкой в модель агент MUST маскировать значения секретов, Bearer-токены и номера карт (остаются первые и последние 4 цифры).

#### Scenario: Секрет не уходит в модель
- **WHEN** в diff есть `API_KEY = "sk_live_abcdef123"` и номер карты `4276550012345678`
- **THEN** в запросе к модели нет ни значения ключа, ни полного номера карты

### Requirement: Валидация ответа
Ответ модели SHALL считаться недоверенным: замечание отбрасывается, если строки нет среди добавленных, severity не из шкалы, текст пустой или оно дублирует правило. Ошибка вызова модели SHALL NOT ломать ревью: замечания правил возвращаются, ошибка пишется в `llm_errors`.

#### Scenario: Галлюцинация строки
- **WHEN** модель вернула замечание на строке 999, которой нет в diff
- **THEN** замечание не попадает в черновик и записано в отброшенные

#### Scenario: Модель недоступна
- **WHEN** запрос к модели завершился ошибкой
- **THEN** черновик содержит замечания правил и запись в `llm_errors`

### Requirement: Подтверждение человеком
Публикация SHALL выполняться только через CLI с флагом `--post` в интерактивном терминале: ревьюер подтверждает каждое замечание (y / n / e, по умолчанию n), затем всю пачку. Без терминала или при прерывании ввода ничего не публикуется. Агент MUST NOT ставить approve и делать merge.

#### Scenario: Нет терминала
- **WHEN** `--post` запущен без интерактивного ввода
- **THEN** публикация пропущена, запросов в GitLab нет

### Requirement: Dry-run
Если не заданы `GITLAB_URL`, `GITLAB_TOKEN`, `--project` и `--mr`, подтверждённые замечания SHALL записываться в `.mr-review/outbox.json` вместо отправки.

#### Scenario: GitLab не настроен
- **WHEN** ревьюер подтвердил 2 замечания из 5, GitLab не настроен
- **THEN** в `.mr-review/outbox.json` ровно эти 2 замечания
