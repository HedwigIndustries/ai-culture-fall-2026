# Design

## Context

Вход — unified diff MR (одна ветка или готовый diff). Выход — черновик ревью: замечания к строкам с severity и рекомендацией текстом, вердикт. Код агент не меняет. Сервис агента развёрнут отдельно, разработчик обращается к нему через CLI `mr-review`. Код банка за периметр не уходит: в прототипе — OpenRouter на открытых и синтетических данных, в проде — GigaChat или on-prem Qwen.

## Goals / Non-Goals

**Goals:**
- Черновик ревью за минуты: обязательные проверки — правилами, смысловые замечания — LLM.
- Публикует только человек; агент не апрувит и не мержит.
- Разработчику — одна команда без доступа к коду сервиса и ключам.
- Измеримое качество на eval-наборе.

**Non-Goals:**
- Обучение или дообучение модели.
- Правки кода: агент не меняет файлы и не готовит патчи, только описывает, что исправить.
- Вебхук GitLab и комментарии к строкам MR.
- Анализ кода за пределами diff (соседние модули, весь репозиторий).

## Выбор подхода

| Подход | Что даёт для ревью MR | Решение |
|---|---|---|
| Обычная автоматизация (правила, линтеры) | секреты, SQL, ПДн, стиль — надёжно и одинаково на каждом MR; смысл кода не видит | **берём** как обязательный слой |
| Классическое ML | классификатор «есть проблема / нет» — нужна большая размеченная выборка своего кода, а текст замечания и место в коде он не выдаёт | не берём |
| Генеративный ИИ (LLM) | понимает код и язык без обучения, пишет замечание к строке и объясняет, что исправить; шумит и может ошибаться | **берём** для смысловых замечаний |
| AI-агент | оркестрация: инструменты (парсер diff, правила, LLM), валидация ответа модели, контроль человека перед внешним действием | **берём** как форму решения |

Итог — агент с двумя слоями: правила гарантируют обязательные проверки, LLM находит то, что правилами не описать; ответ модели проверяется, публикует человек.

## «Суперкот» — идеальный AI-ревьюер

- **Цель:** до прихода человека найти в MR всё, что сломает прод, безопасность или данные клиентов, и не завалить автора мелочами.
- **Возможности:** читает diff в контексте сервиса (соседние модули, контракты API, миграции); знает стандарты команды и банка (ПДн, секреты, таймауты, идемпотентность платежей); отличает блокер от вкусовщины; формулирует замечание как коллега и объясняет, что исправить; умеет промолчать; сообщает уверенность.
- **Инструменты:** GitLab API (чтение MR), правила и линтеры, результаты CI, поиск по кодовой базе, история прошлых ревью команды.
- **Ограничения:** не апрувит и не мержит; ничего не публикует без человека; не видит секретов (маскирование); код не уходит за периметр; замечание привязано к существующей строке. В MVP аудит — только отброшенные и пропущенные замечания в JSON черновика; отдельный журнал решений — в будущем.

MVP закрывает часть: diff без контекста сервиса, правила + LLM, маскирование, валидация, человек в контуре.

## «Суперкоманда»

| Роль | Компетенции | Зона ответственности |
|---|---|---|
| Product owner (тимлид) | процесс ревью, метрики команды | цели, критерии успеха, приоритеты правил; вместе с ИБ решает по ложным срабатываниям и отключению правил |
| Бэкенд-разработчик (Python) | Python, FastAPI, GitLab API, тесты | сервис агента, правила, CLI, интеграция |
| ML / prompt-инженер | LLM, eval, метрики | промпт, выбор модели, eval-набор, мониторинг качества |
| Инженер ИБ | ПДн, секреты, SAST | состав security-правил, согласование передачи кода в LLM, маскирование |
| DevOps / SRE | Docker, CI, Vault, мониторинг | развёртывание сервиса, секреты, доступность |
| Ревьюеры-эксперты (2–3 senior'а) | доменные знания | разметка MR для eval, обратная связь по ложным срабатываниям |
| Ревьюер MR (человек в контуре) | ревью кода | решает, какие замечания агента публиковать (`--post` с подтверждением), ставит approve и мержит |

## Что автоматически, что решает человек

| Автоматически | Человек |
|---|---|
| разбор diff, правила, маскирование, вызов LLM | публикация каждого замечания в MR (в MVP — общим комментарием к MR, `--post`) |
| валидация ответа модели, отбрасывание галлюцинаций и дублей | approve и merge — всегда |
| сортировка, лимит мелочей, вердикт, черновик в `.mr-review/` | оценка замечаний LLM (возможны ошибки и шум) |
| сбор метрик на eval-наборе | изменение правил, исключения, выбор модели |

## Decisions

- **Два слоя: правила и LLM.** Правила дают воспроизводимый результат для обязательных проверок (секреты, ПДн, SQL) и кодстайла, LLM находит то, что правилами не описать: логику, транзакции, обработку ошибок. Альтернатива — только LLM: результат меняется от прогона к прогону, обязательные проверки нельзя гарантировать.
- **Ответ модели — недоверенный.** Замечание попадает в черновик, только если строка есть среди добавленных и severity из шкалы. Альтернатива — доверять модели: замечания на несуществующих строках и мусор в выводе.
- **Лимит входа LLM — 1 000 токенов на файл.** Больший файл проверяется только правилами. Альтернатива — отправлять всё: стоимость и время вызова непредсказуемы.
- **Кодстайл — 30 построчных правил, а не внешний линтер.** Проверяются только добавленные строки diff, без запуска ruff/flake8 на всём файле: у сервиса нет файлов целиком, только diff. Все правила кодстайла — `nit`, и nit ограничены пятью на MR, чтобы стиль не заслонял ошибки. Альтернатива — запускать ruff в сервисе: нужен весь файл, а в diff его нет.
- **Approve нет.** Лучший вердикт — «серьёзного не найдено». Альтернатива — вердикт approve: агент пропустит то, что не умеет видеть, а MR смержат без человека.
- **Сервис и клиент разделены.** В сервисе — код, правила, промпт и ключ LLM. Разработчик ставит только `mr-review` (`uv tool install mr-review`), как `openspec`, и настраивает лишь адрес сервиса. Альтернатива — запускать агента из репозитория у каждого: ключ LLM пришлось бы раздавать всем, а правила и промпт обновлять у каждого.
- **`mr-review` без зависимостей.** Только стандартная библиотека Python и git: ставится быстро и не конфликтует с окружением проекта. Альтернатива — `requests`/`click`: лишние зависимости ради одного HTTP-запроса.
- **Черновик пользователя — в `.mr-review/`, результаты оценки — в `agent/eval/results/`.** Черновик нужен только тому, кто запускал проверку, и в git не попадает; результаты оценки — доказательство качества, их коммитим. Альтернатива — общая папка `out/`: смешивает личные черновики и метрики.
- **Отладочный CLI сервиса (`python -m src.cli`)** — для разработчиков агента и публикации в GitLab с подтверждением (`--post`). Альтернатива — публикация через `mr-review`: клиенту понадобился бы токен GitLab.

## Future (вне MVP)

- **Качество LLM:** известные проблемы и план — `docs/agent/quality.md` (ужесточение промпта и порога уверенности, LLM-судья для метрики, банковский eval).
- **Правки кода:** агент предлагает патч или исправляет файлы сам; ревьюер принимает правку одной командой.

- **Авторизация к сервису:** токен в заголовке и `mr-review login`. В MVP сервис доступен без токена внутри сети.
- **Вебхук из MR:** GitLab при открытии и обновлении MR присылает diff, сервис вызывает тот же `review()` и кладёт черновик в MR для ревьюера. Публикация замечаний к строкам — по-прежнему после подтверждения человеком.

## Правила

| Id | Что ловит |
|---|---|
| SEC001 | секрет в коде или конфиге |
| SEC002 | SQL, собранный из строки (инъекция) |
| SEC003 | ПДн или данные карты в логах |
| SEC004 | `verify=False` — отключена проверка TLS |
| SEC005 | `eval`, `exec`, `pickle.loads`, `yaml.load` без SafeLoader |
| BUG001 | голый `except:` или `except Exception: pass` |
| BUG002 | HTTP-вызов `requests.*` без `timeout` |
| BUG003 | изменяемое значение по умолчанию в аргументе |
| STY001 | `print`, `breakpoint`, `pdb` в коде сервиса |
| STY002 | TODO/FIXME без номера задачи |
| STY003 | строка длиннее 120 символов (E501) |
| STY004 | табуляция в отступе (W191) |
| STY005 | пробелы в конце строки (W291) |
| STY006 | отступ не кратен 4 пробелам (E111) |
| STY007 | несколько импортов в одной строке: `import os, sys` (E401) |
| STY008 | `from x import *` (F403) |
| STY009 | сравнение с `None` через `==` / `!=` (E711) |
| STY010 | сравнение с `True` / `False` через `==` (E712) |
| STY011 | `not x in y` вместо `x not in y` (E713) |
| STY012 | `type(x) == ...` вместо `isinstance` (E721) |
| STY013 | lambda, присвоенная переменной (E731) |
| STY014 | несколько инструкций в строке через `;` (E702) |
| STY015 | тело `if`/`for`/`while` на той же строке (E701) |
| STY016 | имя переменной `l`, `O` или `I` (E741) |
| STY017 | имя класса не в CapWords (N801) |
| STY018 | имя функции не в snake_case (N802) |
| STY019 | пробел перед скобкой вызова: `foo (x)` (E211) |
| STY020 | пробелы вокруг `=` в именованном аргументе: `f(a = 1)` (E251) |
| STY021 | комментарий без пробела после `#` (E265) |
| STY022 | inline-комментарий меньше чем через два пробела (E261) |
| STY023 | `assert` в коде сервиса, вне тестов (S101) |
| STY024 | f-строка без подстановок (F541) |
| STY025 | `%`-форматирование строки вместо f-строки (UP031) |
| STY026 | `.format()` вместо f-строки (UP032) |
| STY027 | `dict()` / `list()` без аргументов вместо `{}` / `[]` (C408) |
| STY028 | `open()` без `with` (SIM115) |
| STY029 | `global` в функции (PLW0603) |
| STY030 | проверка пустоты через `len(x) == 0` (PLC1802) |

STY001, STY002 и STY023 не применяются к тестам.

## Risks / Trade-offs

- Качество смысловых замечаний определяется моделью; в MVP — небольшая быстрая модель с выключенными рассуждениями → много шума и пропусков, модель меняется через `OPENAI_MODEL` без правки кода.
- LLM пишет замечания и к чистому коду → публикует только человек, nit ограничены пятью на MR.
- Правила кодстайла построчные → часть нарушений PEP 8 (пустые строки между функциями, порядок импортов) не видна по diff и не проверяется.
- Правила построчные → SQL, собранный в переменной, и многострочные вызовы они не видят; это первый фильтр, а не гарантия безопасности.
- Файлы больше 1 000 токенов идут без LLM → смысловые дефекты в больших изменениях пропускаются.
- Сервис без авторизации → доступ к нему ограничивается сетью.
