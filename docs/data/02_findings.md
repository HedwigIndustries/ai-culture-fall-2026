# Выводы по данным

Цифры — из `notebooks/data_analysis.ipynb`.

## Закономерности

1. **Треть кода проходит ревью без замечаний** — 1 726 из 5 248 строк (32,9 %). Агент должен уметь промолчать, поэтому кроме recall нужна метрика ложных тревог на чистом коде.
2. **Мелкие замечания преобладают.** Предложения — 62,1 %, вопросы — 20,0 %. Критичные типы (bug 5,0 %, performance 2,3 %, security 1,8 %) вместе дают 9,1 %. Агенту нужен приоритет по severity и лимит на мелочи, иначе критичное теряется.
3. **О чём пишут:** тесты — 8,4 % замечаний, обработка ошибок — 8,2 %, именование — 6,8 %, безопасность — 3,3 %, производительность — 2,5 % (поиск по ключевым словам).
4. **Размер полей сильно скошен.** Медиана diff — 223 токена, но p99 — 1 867, максимум — 3 735. Замечания: медиана 104 символа, p99 — 850, максимум — 3 778.

## Лимит входа агента

| Порог | Отсекается строк |
|---|---|
| diff > 500 токенов | 1 517 (28,9 %) |
| diff > 1 000 токенов | 206 (3,9 %) |
| diff > 2 000 токенов | 35 (0,7 %) |
| замечание > 1 000 символов | 21 (0,6 % замечаний) |

Выбираем **diff до 1 000 токенов и замечание до 1 000 символов**: отсекается около 4 % строк, а стоимость одного вызова модели остаётся предсказуемой. Порог 500 выбросил бы почти треть данных.

## Достаточно ли данных

- **Для оценки агента — да.** Самый редкий класс по severity — major (performance), 80 замечаний (шкала severity: bug, security → blocker; performance → major; refactor, suggestion → minor; style, nitpick → nit; question → question; см. `docs/data/03_cleaning.md`). Этого хватает, чтобы собрать eval-набор по 20 примеров на класс.
- **Для анализа типов и тем — да:** 3 522 замечания.
- **Для обучения модели — нет**, но обучение в проекте не планируется.
- **Для банковской специфики — нет:** секреты, ПДн в логах и SQL-инъекции в open-source почти не встречаются. Их агент покрывает отдельными правилами, а на этом наборе они не проверяются.
